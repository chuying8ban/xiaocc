## 1. 常驻占用：面板把**一个核吃满**，而且和 fps 无关 —— 这条要 @coder 处理

| 实例 | 帧率 | 实测 |
| --- | --- | --- |
| launchd 面板（pid 32130） | 默认 30 | `ps %CPU = 98.1`；30 秒里累计 CPU 从 10.18s 涨到 39.60s ⇒ **29.4s / 30s ≈ 98% 单核** |
| 手工实例（`--backend-opt fps=10`） | 10 | 20 秒里 3.12s → 22.98s ⇒ **99.3% 单核** |
| （对照）旧桌宠小汐自己的日志 | 62.5fps、302×313 | `cpu=4.6% ~ 5.0%` |

**判读**：fps 从 30 降到 10、CPU 一点没降 ⇒ 这不是「帧画得太多」，而是事件循环里有**零超时的忙等/持续重绘**
（`backends/appkit.py` 的 `_pump()` 那圈）。160×194 的透明窗不该用掉一个核：笔记本上就是风扇 + 掉电。
建议：① 确认 `_pump` 是否在 `NSTimer`/`nextEventMatchingMask` 上零间隔自旋；② 空闲档（idle）是否真的停帧；
③ 修好后把小汐那套「每秒多少帧、p95 多少毫秒、cpu%」的自测量也接进来，让它自己举证（我这份是外部旁证）。

## 2. 窗口会漂走且不回锚点，日志里查不到 —— 给 @coder 的第二条

* 启动瞬间与自身日志一致：`1324,96 160x194 layer=3`（`Rect(x=1324.0, y=96.0)`），连续采样稳定。
* 运行约 3 分钟后，外部抓到的是**稳定的 `1225,100`**（左移 99px、下移 4px），连采 3 次不变；
  期间光标在 `901,200`（不在窗口上），所以不是「正被悬停」。
* `xiaoccctl stop && start` 之后重测：新实例 24 秒内始终 `1324,96`。
* ⇒ 漂移发生在**被鼠标碰过之后**（展开/拖动路径），且**不自己回锚点**；面板只在启动时打一行窗口矩形，
  之后位置变化**不留痕** —— 我在机器外没法判断这是正常交互态还是卡住。

建议：位置/状态变化时打一行（哪怕只打 `state=… rect=…`），或者给 `ops/xiaoccctl doctor` 一个

## 4. 复核 CPU 修复（2026-09-29 02:0x）：修好了忙等，但**部署路径不达门槛** —— 因为量法不同

@coder 报「60 秒稳态 4.3%」。我按 @lead 的门槛从 launchd 实际部署的那一份复量，**15.2%**，差 3.5 倍：

| 实例 | 启动方式 | 实测（60s，冷启动 15s 后起算） |
| --- | --- | --- |
| `xiaoccctl start`（pid 54289） | LaunchAgent，`ProcessType=Interactive` | **15.3%**；6×10s 分段 15.0 / 15.2 / 15.3 / 15.6 / 15.2 / 15.3（恒定，不随活动波动） |
| 同一份代码、同一源、同一 fps=30 | 手工前台 `xiaocc run -b appkit` | **4.2%**（30s 窗口） |
| 旧桌宠小汐（同规格部署：Interactive） | 它自己的日志 | 4.6~5.0% |

**结论**：两把尺子量的是两个东西。plist 里 `ProcessType=Interactive` 是让 33ms 定时器按点触发的关键（动画不卡的原因），
手工前台跑拿不到这个类别；忙等修掉之后，**每一拍的真实开销第一次被完整付出来**，于是同一份代码在两种启动方式下差 3.5 倍。
所以门槛（<5%）必须量 launchd 那一份，且 @coder 的自测也要用这个量法，否则「通过」是量法给的，不是代码给的。

**当时的处置**：按 @lead 的规则不达标不装回去 —— `xiaoccctl stop`（rc=0，job 卸载、进程消失），保持他留下的停止态；
守卫按设计随即释放睡眠闸（`pmset` 里不再有我们家的 `PreventUserIdleSleep`）。

## 6. 判据②改成「外部像素在动」后的验证（2026-09-29 02:5x）

@lead 换口径的理由成立（合成器做动画时进程本就该睡着，圈速判不了它），实现与实测：

* 负对照：桌面层窗口（Window Server，1512×982）连抓 3 张 ⇒ `changed=false`、差异 **0.0%**（静态不许被判成在动）。
* 「判不了」不等于「静止」：锁屏时别的进程窗口根本抓不到位图（`CGWindowListCreateImage` → None），
  这时判据②记**不可判读**、gate 退出 **5**、`arm` 停回去但**不算故障**；只有 `--skip-motion` 才只验 CPU 并留痕。
* `arm 15` 实测（屏幕睡着+锁屏）：`A) CPU 14.6%（门槛<5%）` / `B) 不可判读（睡着+锁屏）` ⇒
  `门槛不可判读` → 自动停回（`arm rc=5`、job 卸载、无进程、日志三行齐全）。
* 顺带纠正一条流传中的说法：**屏幕睡着不等于数字低** —— Interactive 这一路睡着仍量到 14.6%
  （它照画不误）；「不带键+屏幕睡 = 4.6%」是**被节流**那一臂的特例。
* 正对照 `ops/motion_positive_control.py` 已入库，但**要屏幕醒着且解锁才能跑**（锁屏时对照窗也不在屏上）——
  这条我会在下次解锁时补跑，拿到 `changed=true` 才算判据②的正向也验过。
